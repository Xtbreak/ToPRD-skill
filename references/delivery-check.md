# 交付检查

交付前检查所有被用户请求的产物，发现问题先查材料或问用户，再修正文档。

- 正文直接从第 1 节开始，没有额外的产品 PRD 总标题或文档类型、版本、状态、更新日期信息块。
- 用户需求场景已通过用户回答核对；问题与当前信息缺口和决策相匹配，相关问题合理组合，提供选项加最后的自由输入入口，已有回答不重复问。
- PRD 保留约定七节，场景、范围、用户流程、功能、评测、验收和交付计划形成闭环。
- 核心功能有稳定 FR 编号，相关实现和面试题使用相同编号。
- 用户的范围、数字、条件、取舍、项目阶段和贡献归属得到保留。
- 缺失信息已通过对话解决。正文没有“待确认”“待填写”、占位符、填写指导、未回答问题、对话记录或无关建议。
- 未评测、未实测或缺少数据等情况已在对话中反馈；PRD 没有相应提示、高亮、逐项免责或证据强弱标签。
- 验收章节以通过标准为主，未强制添加实测结果和上线成绩；功能字段按实际范围裁剪，没有机械添加权限、安全或合规条款。
- 规划与实际实现分别表达。代码存在不代表已部署，单次试跑不代表正式评测。
- 模型选型和项目指标有证据，指标定义和通过门槛能够对应。未评测情况下没有伪造分数或宣称达标。
- 功能验收、AI 通过门槛和上线效果分别描述，重要失败分支有处理规则。
- 已优先使用宿主支持的可点击选择控件，交互类型与工具实际能力一致。
- 已主动询问三份文档的交付选择，或沿用用户此前明确的选择；所选文档均独立交付，没有遗漏，也没有擅自增加。
- 项目详解解释了实际流程、实现和取舍。面试题经过项目化改写，回答和追问有事实支撑。
- PRD 按 SKILL.md 的文档纪律过滤无关内容，正文在第 7 节结束，没有额外结论、项目来源、参考资料、证据清单、附录或代码出处。
- Markdown 表格和图可读，敏感信息未进入文档。实现详解和面试问答中确需使用的引用可访问。交付文件只包含对应文档的正式内容。

检查完成后在聊天中给文件链接和简洁交付说明，文档正文不追加本清单。
